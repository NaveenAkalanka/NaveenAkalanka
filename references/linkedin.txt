About

As a kid, I dreamed of being an inventor, creating countless inventions across various fields. This passion led me to pursue mechatronics engineering. However, during my studies, I felt something was missing. My excitement returned when I discovered computer networking during a study session in my school's IT lab. Understanding how interconnected systems communicate sparked a deep interest in me.
,
This newfound passion for networking filled the void I felt in mechatronics. It involves problem-solving, connecting systems, and seeing the immediate results of my work—elements that truly excite me. I am currently a final-year BSc in Computer Networks student with an HND in Computing. My areas of interest include Network Design, Routing and Switching, Server/Network Virtualization, and Data Center Management. I'm constantly conducting personal projects to develop my skills further, which you can explore on my LinkedIn profile.

In addition to my studies, I work as a senior graphic designer and system administrator at a advertising agency in Sri Lanka. This role helps me support my education financially, given the current economic situation here. While interning at a major IT company is my goal, financial stability is my current priority.

I always try to thrive in active, hardware-involved environments and enjoy collaborating with others. My journey has been driven by a desire to explore, learn, and solve complex problems.

Feel free to connect with me and check out my projects on my LinkedIn profile. Since I'm currently working on a project to host my portfolio website on my own hardware. Until then, let's connect and discuss how we can collaborate or share insights into the ever-evolving field of computer networking.

    Project: 𝗦𝗰𝗮𝗻𝗘𝘆𝗲

    I like building tools to solve problems I personally run into while working with systems and projects.

    When building web-based monitoring tools (like my ClusterEye project), I hit a hard technical wall: web browsers are sandboxed. They cannot directly access the local network to scan for devices or run speed tests. I needed complete network visibility without compromising on the security or convenience of a web interface.

    To address this, I built ScanEye — a lightweight, Dockerized network monitoring tool that bridges the gap between browser security and network accessibility.

    The tool runs as a secure container on your local network, utilizing Nmap for deep scanning and speed testing, while serving a responsive, real-time dashboard to the user. It solves the browser limitation by decoupling the scanning engine from the frontend interface.

    The project is fully deployable. Anyone can spin it up via Docker in seconds to monitor their home lab, discover devices, and visualize network performance.

    What this project helped me practice:

    • Overcoming browser sandboxing limits via split architecture
    • Managing Docker Host Networking for low-level device access
    • Hardening Node.js APIs (Rate limiting, Helmet, Input validation)
    • Implementing real-time data flow with WebSockets

    🛠 𝗧𝗿𝘂𝗲𝗡𝗔𝗦 + 𝗣𝗿𝗼𝘅𝗺𝗼𝘅 + 𝗦𝗠𝗕 (𝗩𝗶𝗿𝘁𝘂𝗮𝗹𝗶𝘇𝗲𝗱 𝗦𝘁𝗼𝗿𝗮𝗴𝗲 𝗳𝗼𝗿 𝗪𝗶𝗻𝗱𝗼𝘄𝘀)

    Running TrueNAS inside Proxmox VE is a common homelab and on-prem pattern when you want centralized storage without dedicating a full physical machine.
    In this setup, TrueNAS SCALE runs as a VM, raw disks are passed through from Proxmox, and storage is shared to Windows systems over SMB.

    This gives you virtualization flexibility + NAS reliability in one design.

    What is SMB (and why it’s used here)
    SMB (Server Message Block) is a network file-sharing protocol mainly used by Windows systems.

    It allows:
      • File sharing over the network
      • User-based access control
      • Drive mapping in Windows (Z:, Y:, etc.)
      • Seamless access without extra client software

    That’s why SMB is the most practical choice when Windows PCs need access to TrueNAS storage.

    Configuration Overview

    What was configured in this setup:
      • TrueNAS SCALE installed as a VM inside Proxmox
      • UEFI (OVMF) + q35 machine type for stability
      • Raw disks attached to the VM using /dev/disk/by-id
      • ZFS pool and datasets created inside TrueNAS
      • Static IP configured for consistent access
      • SMB service enabled with local users
      • Dataset shared to Windows via \\IP_ADDRESS
      • Optional SSH enabled for easier administration

    Result:
    TrueNAS handles storage and ZFS, Proxmox handles virtualization, and Windows accesses everything transparently over SMB.

    Some common issues during setup:
      • Incorrect disk passthrough paths (fixed by using /dev/disk/by-id)
      • SMB authentication failures due to missing “Samba Authentication” on users
      • Permission issues on datasets
      • Network misconfiguration before setting a static IP
      • SMB share not visible until services were restarted

    All of these were documented with fixes.

    If you’re running Docker on a home lab VPS, NAS, or server, you’ll hit this fast:

    ✅ containers everywhere
    ✅ multiple compose files
    ✅ updates, restarts, logs, volumes, networks
    ✅ “what broke?” at 2AM

    Yes, you can do everything from the CLI.

    But once you have more than a few stacks, a Docker manager becomes the control panel for your infrastructure.

    What these tools actually are?

    Self-hosted Docker managers are dashboards you run on your own server that let you:

      • deploy and update containers/stacks faster
      • view logs, resource usage, and health checks in one place
      • manage volumes, networks, and environment variables safely
      • avoid accidental mistakes when you’re doing quick changes
      • give limited access to others (if you’re running shared servers)

    Why it matters? (especially in labs and small teams)
    When your setup grows, the real challenge isn’t “running a container” …

    It’s maintaining it: updates, downtime, troubleshooting, visibility, consistency.

    That’s what these tools help with.

    🥇 Portainer

    🔗 https://www.portainer.io

    Why it’s #1
      • Clean UI, beginner-friendly
      • Manages Docker, Docker Swarm, and Kubernetes
      • Strong role-based access control
    Pros
      • Easy to deploy (one container)
      • Great for home labs and small teams
      • Active development
    Cons
      • Advanced features locked behind paid version

    🥈 Dockge

    🔗 https://dockge.kuma.pet/

    Why it’s rising fast
      • Built around docker-compose
      • Extremely clean and fast UI
    Pros
      • Perfect for compose-based setups
      • Simple stack updates
      • Lightweight
    Cons
      • No Swarm / Kubernetes support
      • Newer project, fewer enterprise features

    🥉 Yacht

    🔗 https://dev.yacht.sh/

    Best for
      • Portainer-like experience with templates
    Pros
      • Simple UI
      • Good app templates for self-hosting
      • Easy deployment
    Cons
      • Slower development
      • Limited advanced controls

    4️⃣ Rancher (Overkill for Most)

    🔗 https://www.rancher.com

    Best for
      • Kubernetes-heavy environments
    Pros
      • Enterprise-grade
      • Powerful cluster management
    Cons
      • Overkill for simple Docker setups
      • Higher learning curve

    5️⃣ LazyDocker (CLI Lovers)

    🔗 https://lazydocker.com/

    Best for
      • Terminal-first users
    Pros
      • Fast
      • No browser needed
      • Great for SSH workflows
    Cons
      • Not beginner-friendly
      • No GUI visuals 


    🧠 My Take

      1. Home lab / learning → Portainer or Dockge
      2. Compose-heavy setups → Dockge
      3. K8s environments → Rancher
      4. SSH-only servers → LazyDocker
